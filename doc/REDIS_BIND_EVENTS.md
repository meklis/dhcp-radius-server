# Контракт: точкові оновлення binds через Redis pub/sub

Документ описує формат повідомлень, які **зовнішня система** (джерело
істини щодо прив'язок клієнтів) публікує в Redis, щоб `radius-server` міг
застосувати зміну одного запису `binds` негайно, не чекаючи чергового
планового `reload` по HTTP. Адресат цього документа - розробники зовнішньої
системи, яка буде **публікувати** (`PUBLISH`) ці повідомлення.

Реалізація на боці `radius-server`: `clientdb/live.go`, `clientdb/redis.go`.

## 1. Загальна модель

- `radius-server` лише **підписується** (`SUBSCRIBE`) на канал і ніколи
  сам нічого в Redis не публікує - канал односторонній.
- Канал використовується **тільки для `binds`** (іменовані джерела з
  `script.database.binds`, наприклад `clients`/`smart`). Таблиця `devices`
  через Redis взагалі не оновлюється - лише повним HTTP `reload`.
- Це **не заміна** повної HTTP-синхронізації, а доповнення для зниження
  затримки. Періодичний `reload` (зазвичай раз на кілька хвилин, див.
  `script.database.refresh_interval`) залишається джерелом істини і рано чи
  пізно перепише будь-які розбіжності - зокрема він єдиний, хто реально
  прибирає з бази записи, для яких зовнішня система не надіслала явний
  `delete`.
- Один канал (`script.database.redis.channel`) обслуговує **всі**
  сконфігуровані джерела `binds` одночасно - конкретне джерело вказується
  полем `db_type` всередині кожного повідомлення (див. нижче), окремого
  каналу на джерело не потрібно.

## 2. Підключення

Параметри Redis (адреса, пароль, БД, назва каналу) - на боці `radius-server`
задаються в його власному конфігу (`script.database.redis.*`). Для
інтеграції потрібно заздалегідь узгодити з експлуатацією `radius-server`:

- адресу і порт Redis (`addr`), пароль (`password`) і номер БД (`db`), якщо
  використовуються;
- точну назву каналу (`channel`), в який публікувати повідомлення;
- набір допустимих значень `db_type` - див. наступний пункт.

З'єднання - звичайний TCP, без TLS. Публікація - стандартна команда Redis
`PUBLISH <channel> <json>`.

## 3. Формат повідомлення

Одне повідомлення = один JSON-об'єкт на один запис:

```json
{"db_type": "clients", "action": "delete", "object": {"id": 123}}
```

```json
{"db_type": "clients", "action": "add", "object": {"id": 123, "ip": 16909060, "mac": "AABBCCDDEEFF", "device_mac": "085A119465E0", "port": 44}}
```

```json
{"db_type": "clients", "action": "update", "object": {"id": 123, "ip": 16909060, "mac": "AABBCCDDEEFF", "device_mac": "085A119465E0", "port": 44}}
```

Запис без прив'язки до пристрою/порту (аналог `smart` у HTTP-джерелі) -
`device_mac`/`port` просто не вказуються:

```json
{"db_type": "smart", "action": "add", "object": {"id": 55, "ip": 169088289, "mac": "0418D6EE60F1"}}
```

### 3.1. Поля верхнього рівня

| Поле | Тип | Обов'язково | Значення |
|---|---|---|---|
| `db_type` | рядок | так | Назва джерела `binds`, повинна **точно збігатися** з одним із ключів `script.database.binds` у конфігу `radius-server` (наприклад `"clients"`, `"smart"`, або єдина назва `"binds"`, якщо джерело одне - залежить від конкретного деплою, див. п.2). Повідомлення з незнайомим `db_type` ігнорується (помилка лише в лозі `radius-server`, зворотного зв'язку в Redis немає). |
| `action` | рядок | так | `"add"`, `"update"` або `"delete"`. Будь-яке інше значення відхиляється (див. п.5). |
| `object` | об'єкт | так | Дані запису, склад залежить від `action` - див. нижче. |

### 3.2. Поле `object`

| Поле | Тип | Обов'язково | Значення |
|---|---|---|---|
| `object.id` | число або рядок із цифрами | так, для будь-якого `action` | Унікальний ключ запису **в межах одного `db_type`**. За ним визначається, який саме запис оновити/видалити. Один і той самий `id` може використовуватись у різних `db_type` незалежно - це різні записи. |
| `object.ip` | число або рядок із цифрами | так для `add`/`update`, не потрібно для `delete` | IPv4-адреса, упакована в 4 байти big-endian і записана одним десятковим числом: `ip = a*16777216 + b*65536 + c*256 + d`. Наприклад `1.2.3.4` → `16909060`. Той самий формат, що й у HTTP-джерелі `binds`/`devices`. |
| `object.mac` | рядок | так для `add`/`update`, не потрібно для `delete` | MAC-адреса клієнта. Формат нотації не важливий (`AA:BB:CC:DD:EE:FF`, `AA-BB-...`, `aabb.ccdd.eeff`, злито `AABBCCDDEEFF`, будь-який регістр) - на прийомі нормалізується (не-hex символи прибираються, літери приводяться до верхнього регістру). |
| `object.device_mac` | рядок | ні | MAC світча/OLT, до порту якого прив'язаний клієнт. Та сама нотація, що й `mac`. Якщо поле відсутнє або порожнє - запис вважається "без прив'язки до пристрою" (як `smart`), і `object.port` у цьому випадку ігнорується. |
| `object.port` | число або рядок із цифрами | ні (але потрібне, якщо задано `device_mac`, інакше запис не буде знаходитись за пристроєм+портом) | Номер порту на пристрої. |

**Числові поля (`id`, `ip`, `port`) можна передавати і як JSON-число, і як
рядок із цифрами** - обидва варіанти підтримуються однаково:

```json
{"id": 123}
{"id": "123"}
```

**Важливо:** значення з плаваючою комою (`123.0`) не підтримуються і
призведуть до помилки розбору на боці `radius-server` - лише цілі числа.

## 4. Семантика `action`

- **`add` і `update` обробляються повністю однаково** - це upsert за
  `object.id`: якщо запис із таким `id` у даному `db_type` вже існує, він
  **повністю замінюється** надісланими даними (часткового оновлення окремих
  полів немає - потрібно надсилати всі актуальні поля запису); якщо не
  існує - створюється. Стороні, що відправляє, не потрібно турбуватися про
  те, чи існує вже запис - можна завжди слати ту дію, яка семантично
  підходить на її боці (створення/редагування), результат на
  `radius-server` буде однаковим.
- **`delete`** - запис із вказаним `object.id` у даному `db_type`
  видаляється, якщо він є. Якщо запису з таким `id` немає - дія безпечно
  нічого не робить (не помилка).

## 5. Гарантії, обмеження, обробка помилок

- **Без підтверджень.** `PUBLISH` у Redis pub/sub - "fire and forget": канал
  не зберігає історію, немає ack/nack, немає ретраїв з боку `radius-server`.
  Якщо в момент публікації підписник недоступний (перезапуск
  `radius-server`, розрив мережі) - повідомлення **безповоротно
  втрачається**. Оскільки це лише прискорювальна надбудова над повним HTTP
  `reload`, втрата окремих повідомлень не критична - актуальний стан все
  одно буде підтягнутий на найближчому плановому `reload`. Не варто
  використовувати цей канал як єдине джерело даних про запис - "істина"
  завжди в HTTP-джерелі `binds`.
- **Порядок.** Повідомлення в одному каналі обробляються `radius-server`
  строго в тому порядку, в якому їх доставив Redis (одним потоком, без
  переупорядкування на нашому боці). Якщо система, що відправляє, шле
  кілька подій по одному й тому самому `id` поспіль (наприклад `add`, потім
  одразу `update`) - порядок публікації важливий, застосується той, що
  прийде останнім.
- **Ідемпотентність.** Повторна відправка того самого `add`/`update` з тими
  самими даними безпечна (результат не відрізняється від одноразової
  відправки). Повторний `delete` вже видаленого запису - теж безпечний.
- **Невалідні повідомлення** (не JSON, невідомий `action`, невідомий
  `db_type`, відсутній/порожній `object.id`, відсутній/нерозпізнаний
  `object.mac` чи `object.ip` для `add`/`update`) - **відкидаються**,
  помилка пишеться лише в лог `radius-server`. Зворотного зв'язку про
  помилку відправнику немає (канал односторонній) - на боці інтеграції
  варто заздалегідь перевіряти коректність значень (особливо `db_type` і
  те, що числові поля - цілі числа).
- **Гонка з плановим reload.** Якщо повідомлення приходить рівно в момент,
  коли `radius-server` виконує свій періодичний повний `reload`, воно не
  втрачається і не застосовується "не до тієї" версії даних - відкладається
  і накочується на новий знімок одразу після завершення `reload`. Для
  системи, що відправляє, це прозоро, жодної особливої обробки не потрібно.

## 6. Приклад повного циклу

```
PUBLISH clientdb-bind-events {"db_type":"clients","action":"add","object":{"id":123,"ip":16909060,"mac":"AABBCCDDEEFF","device_mac":"085A119465E0","port":44}}
...клієнт авторизується через RADIUS, отримує IP 1.2.3.4...

PUBLISH clientdb-bind-events {"db_type":"clients","action":"update","object":{"id":123,"ip":16909061,"mac":"AABBCCDDEEFF","device_mac":"085A119465E0","port":44}}
...наступна авторизація того самого клієнта - вже IP 1.2.3.5...

PUBLISH clientdb-bind-events {"db_type":"clients","action":"delete","object":{"id":123}}
...наступна авторизація - прив'язки вже немає, спрацьовує загальний ("сірий") пул...
```
