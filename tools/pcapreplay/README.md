# pcapreplay

Сверяет реальные ответы прод-сервера (снятые tcpdump'ом) с тем, что отдаёт
локально запущенный `radius-server` на те же самые запросы. Нужен, чтобы
проверить изменения в `script/examples/auth.lua` на реальном трафике, а не
только на юнит-тестах.

## 1. Снять дамп на боевой машине

```bash
sudo timeout 600 tcpdump -i any -s 0 -B 8192 \
    -w /var/tmp/radius_$(date +%Y%m%d_%H%M%S).pcap \
    udp port 1812
```

- `timeout 600` - ровно 10 минут, дальше tcpdump сам получает SIGTERM и
  корректно закрывает файл (не нужно ничего останавливать руками).
- `-i any` - все интерфейсы разом. Если трафик точно идёт через один известный
  интерфейс - укажите его явно (`-i eth0`), это немного снижает нагрузку на
  захват.
- `-s 0` - **обязательно**, полный снаплен без обрезки. Без этого option82
  (Agent-Circuit-Id/Agent-Remote-Id) может обрезаться, и парсинг будет неверным.
- `-B 8192` - буфер захвата 8МБ (KB*1024 в libpcap), снижает риск потерянных
  пакетов на нагруженной машине. Можно поднять больше, если `tcpdump -r`
  потом покажет `packets dropped by kernel`.
- `udp port 1812` - фильтр по auth-порту (сопоставляется и src, и dst, так что
  в дамп попадают оба направления - Access-Request и Access-Accept/Reject).
  Если `radius.listen_addr` в конфиге сервера использует другой порт - поменяйте
  здесь и передайте `-port` в pcapreplay.

Проверить, что дамп снялся и не пустой:

```bash
tcpdump -r radius_*.pcap -nn | head
```

Дамп содержит реальные мак-адреса абонентов - храните и передавайте его так же,
как любые другие персональные данные абонентской базы.

## 2. Поднять локальный radius-server для сверки

Локальный инстанс должен резолвить те же binds/devices, что видел прод в
момент снятия дампа (иначе сравнение будет бессмысленным - сверяем поведение
скрипта, а не актуальность базы). Проще всего - направить `CLIENTDB_URL`
локального сервера на тот же источник (или на снапшот с тем же временем), что
использовал прод, и держать тот же `auth.lua`/конфиг, который проверяете.

```bash
RADIUS_SECRET=test CLIENTDB_URL=... go run ./server -c server/radius.server.conf.yml
```

## 3. Прогнать дамп

```bash
go run ./tools/pcapreplay \
    -pcap radius_20260921_120000.pcap \
    -target 127.0.0.1:1812 \
    -secret test \
    -out mismatches.csv
```

Полезные флаги:
- `-limit 200` - сначала прогнать небольшой кусок, чтобы быстро проверить, что
  всё вообще работает (адрес, секрет, доступность локального сервера), прежде
  чем гонять все 10 минут.
- `-workers N` - степень параллелизма прогона (по умолчанию 20).
- `-out result.csv` - CSV со всеми парами (реальный ответ vs. полученный),
  колонка `mismatch` - что разошлось.

## Как это работает

1. Читает pcap (classic-формат, **не** pcapng - обычный `tcpdump -w` пишет
   именно его), снимает Ethernet/Linux-cooked(`-i any`)/Raw → IPv4 → UDP,
   отбирает пакеты на `-port`.
2. Разбирает каждый UDP-payload как RADIUS-пакет. Access-Request и
   ответивший на него Access-Accept/Reject сопоставляются в пару по
   (клиент, сервер, RADIUS Identifier) - см. комментарий у `reqKey` в
   main.go про ограничения этой эвристики на очень плотном трафике.
3. Для каждой пары собирает **новый** RADIUS-пакет с теми же атрибутами
   (User-Name, NAS-IP, Called/Calling-Station-Id, option82 и т.д. - копируются
   как есть, байт в байт), но со свежими Identifier/Authenticator и секретом
   `-target`-сервера, и отправляет его через `-target`.
4. Сравнивает реальный ответ прода (из дампа) и ответ локального сервера:
   Accept/Reject/Timeout, `Framed-IP-Address`, `Framed-Pool`. `Session-Timeout`
   (lease) попадает в отчёт/CSV, но **не** участвует в определении mismatch -
   INET-лиз считается по часу обработки запроса (см. `leaseTime()` в
   `script/examples/auth.lua`), и между снятием дампа и прогоном всегда проходит
   реальное время, так что то же самое решение закономерно даёт другой lease -
   это не расхождение логики. `Class` в сравнении не участвует вовсе - это
   monotonic-счётчик запросов процесса (`radius/radius.go:getClassId`),
   уникальный per-request, сравнивать его бессмысленно.

**Совет**: чем больше времени проходит между снятием дампа и прогоном, тем
больше в отчёте расхождений из-за естественного дрейфа `clientdb` (абоненты
переключают порты, обновляются привязки) - это не баг. Для чистого сравнения
запускайте прогон как можно скорее после снятия дампа.

Прогон не трогает боевой сервер - запросы уходят только на `-target`.
